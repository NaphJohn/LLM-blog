01整体骨架

M3.1 的主干拓扑和 M3 完全一致，是一个标准的 decoder-only 混合架构：前 3 层稠密、后 57 层 MoE，注意力在全部 60 层都走块稀疏。真正的改动集中在三处——注意力覆盖率、量化训练、投机解码头。

2.3 位置编码

字段值说明

为什么是半维 RoPE

全维旋转在 1M 长度上会积累严重的位置相位漂移，而且高维旋转对长尾频率的数值精度要求高。只转一半维度，等于把「位置」和「内容」拆成两条正交通道——代价是位置分辨率下降，收益是外推稳定性显著提升。配合 1e7 的 theta，实际是把最慢的旋转周期拉到千万 token 量级。

sparse_init_block = 0 意味着这个模型没有 attention sink。很多长上下文模型的稳定性依赖「永远能看到第一个 token」，M3.1 选择不依赖这个机制。这也是它敢把前 3 层全注意力一起换掉的底气之一——但那 3 层原本可能承担了 sink 的角色，这个取舍目前没有公开的消融数据。

03单层数据流与张量形状

把一层拆开看，数据按「归一化 → 稀疏注意力 → 归一化 → MoE → 残差累加」流动。下面标注每一步的实际张量形状（batch=1，序列长 L）。

3.1 三种层的构成差异

层注意力FFNFFN 参数/层
层 0 – 2（3 层）MSA稠密，12288≈ 226.5 M
层 3 – 59（57 层）MSA128 路由 + 1 共享，各 3072≈ 7.30 B

注意「稠密层」仅指 FFN 稠密，注意力依然是稀疏的。moe_layer_freq 数组控制的是 FFN 类型，与注意力无关——这两件事在二手文章里经常被混为一谈。

04MSA 稀疏注意力机制

4.1 复杂度账

设序列长度 N，块大小 B=128，选 k=16 块。

  • 全注意力：每 token 交互 N 个 key，总计算 O(N²·d)
  • MSA：索引打分 O(N·N/B·d_idx) + 注意力 O(N·k·B·d)

N = 1,048,576 时，N/B = 8192 块。索引阶段每 token 要做 8192 次内积（d_idx=128），注意力阶段只做 2048 次（d=128×4 头 ≈ 512 等效）。索引本身不是免费的，只是比全注意力便宜一个数量级。

阶段每 token 的 KV 交互量相对全注意力
1M 全注意力1,048,576 × 4 KV 头1×
MSA 索引8192 块 × 128 维约 1/32
MSA 注意力2048 token × 4 KV 头约 1/512

4.2 工程上的关键约束

KV outer gather Q

朴素实现是 query-major：每个 query 各自去 HBM 抓自己选中的 16 个块。问题是同一个热门块会被几十个 query 重复加载。MSA 的实际 kernel 把选择矩阵转置成 CSR，改成 key-block-major——一个块只从 HBM 读一次，然后为所有选中它的 query 累加部分注意力再归并。这个转换是 MSA 真正跑得快的原因，不只是 FLOPs 少。

这也是为什么 --block-size 128 是硬约束：MSA 的选择粒度必须和 vLLM 的 KV cache 物理块完全一致，否则 CSR 转置后的索引会和显存布局错位。

05MoE 路由细节

5.1 sigmoid + bias 为什么这样设计

softmax 路由下，路由概率总和恒为 1，想让某个专家分数高就必须压低别人，负载均衡靠 aux loss 硬拉。sigmoid 让每个专家独立给分，输出只做 top-k 后的重新归一化（这里再乘 2.0 放大）。好处是专家的绝对置信度有表达空间，坏处是容易出现「某些专家永远被选中」。

use_routing_bias = true 就是补这个漏洞的：给每个专家挂一个可学习偏置，只参与 top-k 排序，不参与最终加权。训练中偏置按负载情况微调，把冷门专家往上顶一点。这是 DeepSeek 系 V3 之后的标准做法，代价是不增加任何推理 FLOPs。

5.2 每层 MoE 的搬运形状

# 输入
x: [L, 6144]
# 路由
logits = x @ W_gate.T              → [L, 128]
scores = sigmoid(logits) + bias    → [L, 128]（bias 只影响排序）
idx    = topk(scores, 4)           → [L, 4]
w      = gather(scores, idx)       → [L, 4]，未归一化
# 计算（按专家分组，permute 后算，再 unpermute）
tokens_per_expert: [4·L, 6144] → 每专家 [n_e, 6144] @ [6144, 3072] → [n_e, 3072]
# 合并
y = 2.0 × Σ w_i · E_i(x) + E_shared(x)   → [L, 6144]

注意 w 没有做 softmax 归一化——sigmoid 输出本身在 (0,1)，直接相加再乘 2.0。这与 DeepSeek-V3 的「归一化后乘 scale」略有不同，M3.1 选择保留未归一化权重，让路由强度的绝对值有语义。

06参数量核算

官方说 428B / 23B。按配置逐项加，能对上，而且能解释 428 与 23 之间的确切含义。

6.1 总参数（428B）

组成算式参数量
路由专家（57 层）57 × 128 × 3 × 6144 × 3072413.1 B
共享专家（57 层）57 × 3 × 6144 × 30723.23 B
注意力（60 层）60 × (6144×8192 + 2×6144×512 + 8192×6144)6.42 B
稠密 FFN（3 层）3 × 3 × 6144 × 122880.68 B
Token embedding200064 × 61441.23 B

推算值 426.7B 与官方 428B 差约 1.3B，缺口主要来自各层的 QK-Norm / RMSNorm 权重、视觉塔的位置编码与 patch_merge 层。在这个量级上属于正常舍入——说明 428B 确实是按「文本主干 + embedding + lm_head + 视觉塔」全量计的。

6.2 激活参数（23B）——为什么是 23 而不是 26

组成算式参数量
4 个路由专家（57 层）57 × 4 × 3 × 6144 × 307212.91 B
共享专家（57 层）57 × 3 × 6144 × 30723.23 B
注意力（60 层）同上6.42 B
稠密 FFN（3 层）同上0.68 B
合计≈ 23.2 B
关键结论

23B 这个数不含 embedding 和 lm_head。严格意义上它们是每 token 都要参与计算的，但业界惯例不计入「激活参数」。所以「23B 激活」应该理解为「23B 的逐 token 计算量」，而不是「23B 参数被读进显存」。后者是 428B 全量——这个区别决定了自建部署需要多大规模的机器。

07DSpark 投机解码

7.1 三个组件各自解决什么

组件解决的问题配置
并行草稿骨干串行 draft 的 N 步延迟5 层 · FFN 12288 · SWA 4096
Markov 头纯并行采样导致的块内 token 互不相关（后缀衰减）rank 256 · 两张 200064×256 表
置信度头盲目校验全部位置，浪费验证算力输入 6400 = 6144 + 256

Markov 头的作用值得单独说：纯并行 draft 下，「位置 1 采样出 of、位置 2 独立采样出 problem」这种拼接错误会让后半段接受率断崖式下降。Markov 头用秩 256 的低秩分解给每个位置注入前一位的条件偏移，把接受长度从「前两位准」拉回到「平均 3.97 位准」。

置信度头的输入 6400 维 = 主模型隐状态 6144 + Markov 特征 256，说明它直接吃的是修正后的表示，而不是原始 logits。

8.2 哪些层被量化，哪些被豁免

组件精度原因
路由专家 MLPNVFP4 (W4A4)占 97% 参数，量化收益最大
稠密层 / 注意力线性层MXFP8数值敏感度中等
索引器 q_idx / k_idxNVFP4只影响块选择，误差可容忍

lm_head高精度直接决定 logits，舍入误差线性传导到输出
embed_tokens高精度稀疏查询，量化收益小
vision_tower高精度视觉特征动态范围大
multi_modal_projector / patch_merge_mlp高精度跨模态对齐层，误差会放大

ignored_layers 共 62 项：57 个 MoE gate（layers.3 – layers.59，与 moe_layer_freq 的 57 个 1 完全对齐）+ lm_head + model.embed_tokens + multi_modal_projector + patch_merge_mlp + vision_tower，其余 5 项均不带层号。不量化清单里没有注意力输出投影，说明它对精度的容忍度比 FFN 低但比 gate 高，走的是 MXFP8 而非 NVFP4。

8.3 体积与 KV cache 的账

项目M3（MXFP8）M3.1（混合）变化
权重451.5 GB250.1 GB−44.6%
KV cache / token61,440 B34,560 B−43.75%
4×B300 256K 并发2876×2.7

KV cache 从 61,440 降到 34,560 的构成：4 个 KV 头 × 128 维 × 60 层 × 2（K 和 V）= 61,440 个元素。M3 下每元素 1 字节（FP8），M3.1 下量化到 FP4 后约 0.5625 字节（含 scale 开销），得 34,560。注意这个数不是正好一半，因为 NVFP4 每个 16 元素组要带一个 FP8 的 scale。

Hub 参数计数为何显示 220B

Hugging Face 按存储的 tensor 元素数统计，而 NVFP4 是打包存储——一个字节装两个值。专家权重打包后，自动计数只认「字节数」，于是 428B 被报成 220B 左右。看 M3 仓库报 427B（全 MXFP8 不打包）就能对上。这是统计口径问题，不是模型缩水。

9.1 图像 token 压缩

spatial_merge_size = 2、temporal_patch_size = 2，采用 patch_merge 方式。672 图像分 48×48 个 14×14 patch，经 2×2 合并后变成 24×24 = 576 个视觉 token——正好等于 image_seq_length = 576。

动态分辨率下最多支持 2016×2016（image_grid_pinpoints 36 个候选中 6 个边长 {336, 672, 1008, 1344, 1680, 2016} 的全组合），此时视觉 token 达 5184 个。这是 1M 上下文能塞进多少张图的关键约束。

10M3 → M3.1 逐项 diff

10.1 三条改动的因果链

改动直接效果二阶效果
MSA 覆盖到 60 层去掉混合执行路径kernel 统一，显存布局可预测；但浅层失去全注意力兜底
QAT + NVFP4 专家权重从 451.5 → 250.1 GB单卡能放的 KV 变多 → 并发 28 → 76；推理成本下降主要来自这里
DSpark 替换 MTP草稿头可挂载，接受长度 3.97输出侧吞吐提升，但对 prefill 无影响
一句话

M3.1 省的是每 token 的搬运字节数，不是每 token 的思考量。所以它在 agentic 长任务（长上下文 + 长输出）上收益最大，在需要极深单步推理的场景里，反而可能因为专家权重被压到 4bit 而输给 M3 全精度版本。

11.2 五个容易踩的坑

  1. block-size 必须是 128。这是 MSA 稀疏块与 KV cache 物理块的对齐要求，改任何别的值都会让选择矩阵和显存错位。
  2. tensor-parallel 建议 4。4 个 KV 头正好能被 4 整除；上到 8 卡时 KV 头要复制，收益不线性。
  3. dspark block size 写 7 不是 8。dspark/config.json 里 dspark_block_size = 7，部分博客写 8 是看了 SPEED-Bench 的评测设置，别混用。
  4. Hopper 上没有 DSpark。官方 recipe 明确关闭，跑起来会静默退化成普通解码，速度差一大截但不会报错。
  5. 不要指望 PTQ 版本等价。官方权重本身是 QAT 产物，第三方再压到 3bit/2bit（如 Unsloth 的 GGUF）会有额外掉点，README 主动提示了这点。

11.3 推荐的推理参数

temperature = 1.0
top_p = 0.95
reasoning_effort ∈ {low, medium, high, xhigh, max}

五档 reasoning effort 通过 chat template 注入，是 M3.1 少见的「显式成本旋钮」。Automation-Bench 上从 low 的 52.8% 一路爬到 max 的 62.8%，曲线贴着成本-性能前沿——这说明它不是简单地「多想就更好」，而是每一档都有明确的性价比拐点。

外部复现只有 26%，官方 38.1%，差距不小。资料显示 M3.1 在某些专业任务上输出的 token 数远多于 M3——换句话说，高分部分来自「愿意多说」，而不是「单步更强」。评估 agentic 模型时这个区别很关键，如果你的场景对输出长度敏感，实际体验会和榜面不一致。
