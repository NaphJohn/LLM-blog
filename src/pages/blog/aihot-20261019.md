## ★ 今日最值得关注

**vLLM 高并发「吞 Token」：输出不是报错，是静默掉智商。**

这是本期唯一一条和 09-01 那个 NVFP4「无限重复」同类的、会**直接毁掉你线上输出**的问题——区别是它藏在一条好看的吞吐曲线背后。三层事实：

1. **症状**：多机多卡高并发下，gpu_model_runner 状态更新路径会**静默丢 token**；同一模型在高负载时输出质量（「智商」）下降，而不是显式报错或仅吞吐掉速。根因在 `gpu_model_runner.py` 的 `_update_states` 对并发请求状态追踪不完整。
2. **修复**：范式团队 PR **#41133** 已合入 main，下个 release 正式发布；nightly 可测但不建议生产。
3. **后果**：这不是"吞吐 benchmark 好看就万事大吉"的坑——它**只在并发压满时显形**，单并发完全看不出来。

**可执行结论**：高并发部署（尤其是 1P1D / 多机多卡）上线前，除了 tokens/s，务必用 **lm_eval 等精度评测压一遍**；别只看吞吐曲线。

> 值得单独说的一点：和 09-01 那个"修复在 main、发布通道被钉死"的 NVFP4 bug 一样，这类**「静默正确性退化」比崩溃更危险**——崩溃你会立刻发现，掉智商你只会怪模型不行。这再次提醒：依赖管理里必须有一条从 main 构建 / nightly 验证的应急路径。

### 原理：vLLM 高并发「吞 Token」正确性坑（PR #41133）

本期最值得理解的一条技术解读——它和「吞吐」无关，关乎「正确性」。

**症状**：超高并发下，模型 runner 的 state 更新路径会**静默丢弃部分 token**。不是报错，不是 OOM，是输出「变笨」——同一 prompt 在低并发答得对、高并发答错。

**根因**：`gpu_model_runner.py` 的 `_update_states` 对**并发请求状态追踪不完整**，在多机多卡高并发的状态更新里漏掉了对部分 token 的记账。

**修复**：范式团队 PR #41133 已合入 main，下个 release 正式发布；nightly 可测但不建议生产。

**落地建议**：高并发场景除吞吐 benchmark 外，**务必用 lm_eval 等精度评测压测**。只看 tokens/s 会完全错过这个坑——它只在并发拉满时显形。

### 常驻专题

**PD 分离**：vLLM push-NIXL 随 v0.32.0 稳定（1P1D Qwen3-32B TTFT 最高 3×、TPOT +30%）；SGLang Mooncake（NVIDIA 首选）+ NIXL + HiCache；GPUStack 发布 PD 配方目录（vllm-nixl / sglang-mooncake（首选）/ sglang-nixl / vllm-ascend-mooncake）细化 KV 传输后端与 GPU 过滤 → 运维可照配方落地。

**架构演进**：结构化「**决策端点**」成共同主线（vLLM /v1/systemone + SGLang Clef / System One API）；低精度 KV / 2-bit + 投机（Muse Spark Open 用 SGLang DFlash2 / vLLM DSpark day-1）+ chunked prefill / continuous batching 收底。

**纯 PyTorch vs transformers**：窗口内**无「脱离 transformers」新 PR**；vLLM 反将工具 / 推理解析器规范读入 HF checkpoint 的 `response_template`（#58604 / #58602），Transformers 后端视频随 v0.32 进稳定 → 方向是更紧 HF 集成而非出走。
