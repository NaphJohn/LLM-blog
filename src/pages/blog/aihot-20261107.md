## ★ 今日最值得关注

**主线在 main：两个会"无声毁掉线上"的修复。**

两层框架稳定版同为 11-02 收口（vLLM v0.33.0 / SGLang v0.5.23），近 72h 无新发版。真正值得盯的是 main 分支的硬化，其中两条会直接毁掉部署：

1. **vLLM #64986（11-06）**：`--kv-sharing-fast-prefill` 下未完成的 device→host 拷贝，让 trtllm-gen decode 内核拿到垃圾 query length **永久挂起**。B200 Gemma4 E4B 微调复现 **4/4 挂起**，拉修复后 20s 跑完。→ Gemma 类 KV 共享 + fast-prefill 部署必须拉此修复。
2. **SGLang main DeepSeek-V4.1 修复（11-07）**：在 MLP-sync-padded 张量的**真实行**上跑 attention，修正 padding 行引入的**注意力污染**。→ 跑 DeepSeek-V4.1 建议拉 main。

**可执行结论**：自托管团队若锁定 0.33.x / 0.5.23，需把"从 main 拉指定修复"纳入升级 checklist——尤其是 KV 共享、fast-prefill、DeepSeek-V4.1 这三类负载。

> 值得单独说的一点：又是"**修复在 main，发布通道滞后**"的一天。vLLM 0.34.0 虽已在 main（Kimi K3.1 Pro 需 0.34+），但稳定线仍是 0.33.0。你的依赖管理里必须保留一条从 main 拿热修的应急路径，否则这两类 bug 会在你不知情的情况下吃掉吞吐或卡死进程。

### 原理：vLLM #66064 把 Gated DeltaNet prefill 融合成一发带宽受限内核

本期最值得理解的一条技术解读。

PR **#66064** 将 Gated DeltaNet 预填充的状态 gather/scatter 由**每层 4–5 个 eager 内核**融合为**跨所有 GDN prefill 后端的单个带宽受限内核**：

- B300 上层预填充链 **1.16–1.50×**
- Qwen3.5-0.8B 前向 prefill8192 **降 2.7%**、chunked prefill **降 6.1%**、decode 不变

本质是**减少全局显存往返**——中间状态留在寄存器 / 快速存储。这再次印证：**kernel 融合就是 PyTorch 推理速度的藏身处**，且对长上下文 prefill 最有利。

> 我的判断：这种"把多个 eager 内核压成一个带宽受限内核"的打法，是长上下文 + 混合注意力时代最稳的降本路径。它不靠新硬件，只靠减少 HBM 往返——而 HBM 带宽正是大规模 MoE / prefill 的第一瓶颈。

## 三、AI论文与产业热点

### 论文核心 · RT-H：Action Hierarchies Using Language

**Belkhale et al., Google DeepMind × Stanford, arXiv:2403.01823, RSS 2024【具身智能】**

- 一句话定位：在任务与动作之间插入**语言动作中间层**（move arm forward 等），逼策略学透跨任务共享的低层运动结构。
- 核心思想：① 单 VLM 双查询（π_h 语言动作 → π_l 动作），RT-2 配方；② **2500+ 语言动作短语**从本体感受自动提取，零人工标注；③ 语言动作层 = **数据总线 + 人类语言干预接口**。
- 影响：层级化 VLA 直系源头（Helix/DriveVLM/π0.5 双系统同范式）；语言干预微调超遥操作干预（IWR）约 **50%**。

### 算子讲解 · z-loss

**ST-MoE, Zoph et al., arXiv:2202.08906**：只罚 logsumexp² 的幅度项，c_z=1e-3；零点在 logZ=0，仅移除 logit 公共平移自由度、不偏袒类别；ST-MoE 不加 6 次挂 4、加后 3 次全稳；PaLM/GLaM 标配、OLMoE 同系数；与 MoE aux loss 正交。

### 性能优化 · 数据混合律 Data Mixing Laws

**Ye et al., arXiv:2403.16952**：L(h)=E+ΣC_i·exp(γ_i·h_i)；70M–410M 小模型 ×30B ×40 组配比外推 1B/100B 最优配比；优化配比 ≈ 默认配比多训 **48%** 步数；VLA 的真机 / 视频 / 语言数据配比问题可直接套用。
