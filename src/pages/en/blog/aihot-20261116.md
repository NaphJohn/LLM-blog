## ★ Most Worth Your Attention Today

**vLLM v0.34.0rc3 fixes the Kimi-K3 DSpark startup OOM — but in the same RC, the memory default was quietly changed too. Before you delete your workaround, look closely at how you deploy.**

This is the one item today that lets you change a config immediately. The trouble is not the fix itself, but that it arrives **at the same time as a breaking change**.

Three layers of fact:

1. **Symptom**: Kimi-K3 DSpark hits **3/3 CUDA OOM at startup** under **TP4 / 4×B200**; until now the only relief was a workaround like `gpu_memory_utilization=0.90`.
2. **Fix**: PR **#67485** (11-13) repairs startup memory allocation — **3/3 OOM → 6/6 clean starts**, recovering about **9 GiB** of KV space per card → the workaround can go.
3. **But**: **from rc2 on, most scenarios no longer set `gpu_memory_utilization` by default** (it used to be ~0.9). Python API deployments that relied on the default now need to **pass it explicitly**, or capacity behavior changes. Meanwhile **PR #67035 removes TeleChat2/3**; v0.34.0 is the last version supporting them, so TeleChat must be pinned.

**Actionable conclusion**: K3.1 Pro still needs nightly (stable v0.33.0 only carries K3 code); the RC is fine for regression but not for production. When upgrading, set the memory parameter explicitly, re-measure capacity, and do not rely on defaults.

> Worth saying separately: **a fix and a breaking change landing in the same RC** is the combination most likely to make an upgrade go sideways — you delete the workaround while the default changes underneath you, so two capacity-related settings move at once. Treat this kind of release as a "migration," not an "update."

## 2. vLLM & SGLang Community Tracking

**Version status**: **no new stable releases from either framework over the weekend.** vLLM stays at **v0.33.0** stable, with **v0.34.0 advanced to rc3** (11-13); SGLang's tag remains **v0.5.23**, but it has announced the **v1.0** milestone and opened a stability tracker.

### vLLM v0.34.0 RC

**New features / key PRs**:

- **rc0: Gemma / StableLM migrated back to the Transformers backend** — absorbing upstream definitions and lowering maintenance cost, at the price of short-term regressions in fused operators.
- **rc1: XPU speculative-decoding NaN fix** — `greedy_argmax` now treats NaN as `-inf`, removing a cross-hardware garbage-output risk.
- **rc3 / PR #67485: startup CUDA OOM fix** — Kimi-K3 DSpark TP4 on 4×B200 goes from 3/3 OOM to 6/6 clean starts, recovering ~9 GiB KV per card (see ★).

**Breaking changes**:

| Change | PR | Impact |
|---|---|---|
| **From rc2 on, most scenarios no longer set `gpu_memory_utilization` by default** (was ~0.9) | — | Python API deployments must pass it explicitly |
| **TeleChat2 / 3 removed** | #67035 | v0.34.0 is the last supported version; pin required |

**Performance**: **DeepSeek-V4.1 DeepGEMM warmup compiles only reachable kernels**, cutting GB200 time from **68.4s → 11.2s** — faster cold starts for elastic scaling, especially valuable for request-metered inference services.

> ⚠️ **Small-VRAM users / anyone relying on defaults**: this release changes both the memory-allocation logic and the default value, and both move your peak memory. Re-measure capacity using a "migration" checklist after upgrading.

**Milestone / awaiting tag**: the **v1.0 stability tracker opened 11-12**, core features are frozen; **invalid configs now fail fast with a startup error / 4xx instead of being silently overridden**; `sgl-model-gateway` is deprecated in favor of `sgl-router`. The GitHub tag, however, is still **v0.5.23**.

> "Invalid configs changing from silent override to startup error" matters far more than the three letters v1.0: it means that after upgrading, a bad parameter that used to be silently swallowed will now cause an **outright startup failure**. Audit your launch flags now.

### Under the Hood: Evolving Infra's Symmetric Serving Engine

The most worthwhile technical read of the day, and the hardest progress of the week.

**The pain point**: role switching (P↔D) in traditional PD disaggregation requires restarting the instance and losing KV — Dynamo measured **681–754s**.

**The approach**: a SGLang-based **symmetric engine** runs **both P and D in a single scheduling loop**; a role switch only changes the router's request type — **no restart, no KV loss, done in 6.2s**.

Three supporting pieces:

1. **Shared host KV pool**: L1 HBM / L2 host memory, reusing Mooncake RDMA.
2. **Async KV fetch during queueing**: median **7ms**, hidden inside the **0.7–2.2s** queue wait, so it barely adds latency.
3. **Prefix-tree reference-counting directory**: prevents LRU from mistakenly evicting an in-flight agent's context.

**Result**: multi-agent latency down **4.1×** on 36×GB300.

> My read: what this rewrites is not "another speedup" but the **definition of the bottleneck** — the constraint on agent clusters has shifted from single-request throughput to **role-switching speed and KV lifecycle management**. Going from 681–754s to 6.2s is roughly two orders of magnitude; anyone still stuck on "restart-based PD" will be left behind in agent workloads.

### Standing Topics

**PD disaggregation**: Evolving Infra's adaptive PD is this week's headline; vLLM rc3's KV-warmup OOM fix belongs to the same disaggregated capacity-planning story; consensus is **long prompts to PD, short prompts computed locally, KV-cache-aware routing, and fp8 KV to halve transfer**.

**Architecture evolution**: symmetric engines + tiered KV + agent-aware directories; SGLang v1.0 formalizes the Rust critical path / megakernels / HiCache; vLLM keeps advancing DFlash / DSpark speculation, FLy lossy verification, and low-precision KV.

**Pure PyTorch vs transformers**: vLLM moves Gemma / StableLM **back to Transformers** (converging the definition layer), in contrast to the new pure-PyTorch engine **YASAKANI** (leading in self-tests running Qwen3.8-27B on a single 5090); conclusion = **production converges on "Transformers definitions + in-house runtime / operators," with pure in-house stacks becoming niche**.

**Step adaptation**:

- **Step 3.7 Flash** four-format weights + NVFP4 & MTP measured at **1.13×–1.45×**.
- **Step 5 Preview** dual-framework Day-0/1 + the StepFun sparse-attention kernel landing in SGLang + domestic-compute Day-0; no new weights in this window.

> The YASAKANI item is worth a look: **leading self-tests running Qwen3.8-27B on a single 5090** shows pure in-house stacks still have life in extreme-optimization scenarios — but it does not change production's direction of convergence; if anything it confirms the division of labor: "definitions to Transformers, runtime written in-house."

## 3. AI Papers + Industry Hotspots

**Today's focus (1 line)**: OpenVLA-OFT proves that an embodied "too slow" can be solved without changing the model — only the decoding recipe: a 7B VLA runs a full 25Hz on a dual-arm real robot, **26× throughput, and LIBERO success up 20.6 points**; on the same day, the industry's yardstick is shifting from narrative to delivery.

### Paper Core

**OpenVLA-OFT** (Stanford, arXiv:2502.19645, RSS 2025) | a VLA acceleration paradigm that keeps the base model and changes only the fine-tuning recipe: **parallel decoding + action chunking + continuous actions + L1 regression**. Three core lines: ① switch action tokens to a **bidirectional mask** so all K·D tokens come out in one forward pass, compressing K·D weight reads into one; ② chunking (LIBERO K=8 / ALOHA K=25) + receding horizon — "thinking one segment at a time" naturally reduces error accumulation, so it **gets more accurate as it gets faster**; ③ continuous actions + pure L1 replacing diffusion / flow matching (50-step denoising took 1.91s; a single step collapses LIBERO-Long to zero). Results: **LIBERO 76.5% → 97.1%, 26× throughput**, ALOHA ahead of π0 / RDT-1B / ACT / DP by up to 15pt. Impact: a single model plus chunk parallelism is enough for 25Hz — no dual-system architecture needed.

### Operator Deep-Dive

**DeepStack** (Qwen3-VL) | handing only the final ViT layer to the LLM loses strokes / edges / texture; DeepStack injects **three intermediate-layer features via residual addition into the LLM's first three decoder layers** | in use across: **the full Qwen3-VL line** (4B at layers [5,11,17], 30B-A3B at [8,16,24]) | key points: ① **zero token increase**, sequence length unchanged, just three position-wise additions; ② `deepstack_visual_indexes` is the **ViT layer index, not the LM injection layer** — dropping the merger norm when exporting to edge causes "the whole box to shift."

### Performance Optimization

**EPD three-stage decoupling** (SGLang / vLLM EC connector / NVIDIA Dynamo) | visual encoding is an independent third stage — **compute-bound, produces no KV, and its output is a pure function of the image** — so it can scale independently and be cached across requests | representative work: SGLang `--encoder-only/--language-only` + Mooncake transport + `--enable-mm-global-cache`; vLLM `ec_transfer` | gains: independent scaling + eliminating image-to-text head-of-line blocking + embedding-level reuse; embeddings are about **8 MB per image**, so do the math before shipping them cross-machine.
